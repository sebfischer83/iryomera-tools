# ADR 0003 — Reproducible local medical import and review staging

Status: accepted for Phase 2.

MedicalImporter is a .NET tool referencing Content.SDK, System.CommandLine and CsvHelper. It owns its versioned staging contracts and never makes the SDK depend on CLI, storage or source adapters. Inputs are local uncompressed files; no automatic medical-source download or license acceptance occurs.

One atomic JSON workspace stores immutable import batches, normalized terms, source assertions, original fields, provenance, diagnostics and explicit review/redistribution decisions. A file lock serializes writers; replacement uses a same-directory temporary file and atomic rename. Failed/canceled operations must preserve the previous workspace. SHA-256 plus adapter/options/source metadata/timestamp identifies a batch; repeated import is idempotent, while different batches retain their own claims. Identical explicit-ID claims can coalesce with all approved provenance retained; conflicting semantics produce errors instead of silent overwrites. Stable IDs reversibly encode the original external identifier as lowercase UTF-8 hex, with one configured package namespace. This avoids punctuation-normalization collisions and keeps source identifiers separate from display text.

Use OBO Graph JSON and OBO as the initial ontology formats, HPOA/MAxO TSV annotations, BfArM ClaML XML and LOINC CSV. Unsupported formats fail explicitly. Ontology hierarchy and xrefs are preserved as source assertions, never interpreted as disease links. HPO terms map conservatively to findings (phenotypic features are not all symptoms). MAxO actions map to the generic medical-procedure definition, not guessed treatments. ICD classes remain diagnosis classifications and OPS classes procedures; LOINC observations remain examinations without diagnostic thresholds or performance claims.

MAxO assertions can involve an action, phenotype, optional disease and optional extension, plus predicate, evidence and qualifiers. These cannot be faithfully flattened into v1 diseaseTreatment relations. Export them in a separately versioned `source-assertions.json` sidecar with original predicates/fields and resolved IDs. Only positive HPOA P-aspect assertions with empty qualifier, frequency, onset, sex and modifier fields can additionally become context-free DiseaseFinding relations; all contextual assertions stay in the source sidecar. Negations, frequency strings and clinical context remain source data, never game probabilities. The sidecar is part of the release bundle, not an undocumented SDK extension. A future game consumer must explicitly choose which source assertion semantics to support.

Imports always start unreviewed. Review is a separate CLI operation with reviewer/timestamp and an append-only audit history. Release export selects approved records/assertions only; every selected assertion must have approved resolvable endpoints. Unknown/negated assertions may remain in staging and do not imply positive relations. Every contributing batch must have an explicit audited redistribution decision and preserved license text/notices. Technical validation cannot determine legal permission or clinical truth. The CLI trusts its local operator; reviewer identity is an audit label, not authenticated authorization. Studio must later add user/access controls.

Export builds a new directory containing content.json, a source-language catalog per actual source language, source-assertions.json, an import/review report and original license texts/notices. It never fabricates missing translations. English is required only for a bilingual release profile; untranslated source-language catalogs are staging/review content and remain visibly incomplete for the future editor. Content export is blocked on semantic errors; a strict localization profile can require en/de before game publication. No real clinical release is made by the repository fixtures.

Work packages: pipeline and staging → HPO slice and tests → MAxO and independent annotations → ClaML ICD/OPS and LOINC CSV → reproducibility/error/CLI integration tests → source field/license tables, schemas, runnable examples and CI. No later-phase UI, ZIP packager or remote distributor is added.
